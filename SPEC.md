# ТЗ: сервер игры «Эфир» (`efir_backend`)

Сервер кооперативной обороны с рацией. Он держит каналы на двоих, ведёт лобби и **считает смену**. Клиенты только рисуют снимки и шлют команды.

Документ описывает продукт как набор тикетов: эпики -> задачи -> бизнес-правила и критерии приёмки.

**Откуда брать подробности**
- Контракт с фронтендом: `efir_frontend/docs/backend-contract.md`. Там HTTP, сообщения сокета, поля снимка и событий.
- Типы контракта: `efir_frontend/src/lib/net/protocol.ts` и `efir_frontend/src/lib/game/protocol.ts`.
- **Эталон смены**: `efir_frontend/src/lib/game/sim/` (`simulation.ts`, `bot.ts`, `flow.ts`, `cards.ts`), числа в `src/lib/game/rules.ts` и в начале `cards.ts`. Сейчас эту симуляцию в браузере гоняет заглушка фронтенда. Твоя задача - повторить её на Go. Тексты реплик, журнала и подсказок бери оттуда дословно.
- Поведение эталона описывают тесты `simulation.test.ts` и `cards.test.ts`. Их стоит перенести в Go почти один в один.

## 1. Процесс разработки

1. **Один тикет - одна ветка:** `git switch -c EFR-4-lobby-rules`. В конце merge в `main`.
2. **Сначала тест, потом код**, как минимум для бизнес-правил.
3. **Definition of Done** (общий для всех тикетов):
   - `make` проходит полностью (tidy, fmt, lint, test -race, vuln);
   - каждое бизнес-правило (`BR-x.y`) покрыто хотя бы одним тестом, имя теста или комментарий ссылаются на номер правила;
   - у экспортируемых имён есть doc-комментарии;
   - нет `//nolint` без объяснения причины;
   - фронтенд с `VITE_BACKEND=http` проходит сценарий тикета руками (где это применимо).
4. **Зависимости.** В продакшен-коде только стандартная библиотека и то, что уже есть (`env`, `huma`). Исключения:
   - `github.com/coder/websocket` - WebSocket (EFR-3). В стандартной библиотеке его нет. Протокол руками не пишем.
   - `golang.org/x/sync` - по необходимости, после того как сделаешь вариант на голых горутинах.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Канал | Комната на одну смену: код, два поста, лобби, потом смена |
| Код канала | 6 цифр, например `482117`. По нему друг входит |
| Пост | `west` или `east`. `west` у того, кто открыл канал |
| Позывной | Имя игрока из фиксированного списка из 8 штук. Аккаунтов нет |
| Токен | Секретная строка игрока в канале: пускает в сокет и возвращает на пост после обрыва |
| Хост | Тот, кто открыл канал. Всегда на `west`. Только он начинает ночь и следующий день |
| Бот | Напарник, который держит `east` в одиночной смене |
| Смена | 7 ночей. Фазы: `briefing -> day -> night -> report -> … -> end` |
| Такт | Один шаг симуляции, 50 мс |
| Снимок | Состояние смены глазами одного игрока, уходит каждый такт |
| Событие | Разовое: строка рации, запись журнала, звук, вспышка, сводка |
| Команда | Намерение игрока: построить, разведать, начать ночь… |
| Дизель | Источник энергии поста у ядра. Горит канистры с общего склада |
| Просьба бункера | Карточка утром дней 2–6: оба поста голосуют, принято только при двух «за» |
| Туман войны | Игрок получает только мутантов в своём обзоре. Считает сервер |

## 3. Нефункциональные требования

- **NFR-1.** HTTP - JSON. Ошибки HTTP - стандартный `application/problem+json` от huma (ADR-006).
- **NFR-2.** Сообщения сокета - JSON-объекты с полем `type`, по одному сообщению на кадр WebSocket.
- **NFR-3.** Токены **никогда** не попадают в логи, в том числе в access log через query `?token=`.
- **NFR-4.** Состояние только в памяти процесса (ADR-005). Перезапуск сервера закрывает все каналы, это допустимо.
- **NFR-5.** По SIGTERM сервер закрывает все сокеты кодом 1001 (`going away`) и завершается за `SERVER_SHUTDOWN_TIMEOUT`.
- **NFR-6.** Один медленный клиент не тормозит канал и другие каналы: отправка не блокирует такт (EFR-3).
- **NFR-7.** Симуляция детерминирована: при одинаковом сиде и одинаковых командах получается одна и та же игра (ADR-004).
- **NFR-8.** Тесты проходят с `-race`.

## 5. Справочник ошибок

**HTTP** (тело - модель ошибки huma, фронтенд смотрит только на статус):

| Статус | Когда |
|---|---|
| 404 | нет открытого канала с таким кодом, или канал одиночный |
| 409 | оба поста заняты |
| 422 | код не из 6 цифр, неизвестный `mode` |
| 503 | достигнут `GAME_MAX_CHANNELS` |

**Сокет:**

| Ситуация | Что делает сервер |
|---|---|
| нет токена или токен чужой | отказ при апгрейде, HTTP 401 |
| Origin не в списке | отказ при апгрейде, HTTP 403 |
| сообщение больше `GAME_WS_MAX_MESSAGE` | закрыть сокет кодом 1009 |
| не JSON или неизвестный `type` | игнорировать, записать в лог на уровне debug |
| нарушено правило лобби | `{"type":"error","code":"callsign_taken"}` и т. п. (EFR-4) |
| нарушено правило смены | событие `flash` этому игроку (EFR-8 и дальше) |
| канал закрыт (хозяин ушёл, сервер выключается) | закрыть сокет: 1000 или 1001 |

## 6. Архитектурные решения

### ADR-001. Слои

```
cmd/efir/                         composition root
internal/channel/                 каналы, лобби, посты, позывные, токены, реестр каналов
internal/game/                    симуляция смены: чистая логика, без сети и времени
    rules.go, flow.go, sim.go, bot.go, …
internal/httpapi/                 HTTP (huma) и апгрейд в WebSocket
internal/ws/                      чтение и запись сокета, кодирование сообщений
internal/infrastructure/          config, logging
```

Правило зависимостей: `httpapi`, `ws` -> `channel` -> `game`. Пакет `game` не знает ни про сеть, ни про `time.Now`, ни про каналы. Ему дают `dt`, команды и генератор случайных чисел.

### ADR-002. Канал - это актор

**Контекст.** В каждом канале два источника событий: сокеты игроков (команды) и таймер (такт). Состояние смены большое и постоянно меняется. Защищать его мьютексом - значит думать о блокировках в каждой функции симуляции.

**Решение.** Каждый канал - отдельная горутина, которая единолично владеет состоянием:

```go
for {
    select {
    case <-ctx.Done():            // сервер выключается
    case msg := <-ch.inbox:       // команда, подключение, отключение
    case <-ticker.C:              // такт: sim.Tick(dt), снимки, события
    }
}
```

- Горутины чтения сокетов только кладут сообщения в `inbox`. Состояние они не трогают.
- Каждому игроку свой буферизированный `outbox` и своя горутина записи.
- Если `outbox` переполнен, клиент не успевает. **Старые снимки выбрасываем**, события нет. Вариант: при переполнении закрыть сокет кодом 1008 - решить в EFR-3 и описать в коде.
- Реестр каналов (код -> канал) - общая структура. Её защищает `sync.Mutex`, это нормально.

**Что это даёт.** Состояние смены без мьютексов, тесты симуляции без горутин, гонки ловит `-race`.

### ADR-003. Симуляция детерминирована

- Случайность передаётся в симуляцию интерфейсом `func() float64` (как `random` в эталоне). В проде это `math/rand/v2` с сидом из `crypto/rand`, в тестах - фиксированный сид.
- Время передаётся параметром `dt` в `Tick`. Внутри `game` нет `time.Now()`.
- Значит, любой баг воспроизводится сидом и списком команд.

### ADR-004. Только память

Каналы живут в памяти процесса, базы нет. Игре на двоих на час не нужно ничего хранить после смены. Несколько реплик сервера потребовали бы закрепить канал за репликой (sticky sessions), но пока одна реплика.

### ADR-005. Ошибки - стандартная модель huma

Своего пакета ошибок нет. Фронтенду достаточно статуса.

Как это устроено в коде (`internal/httpapi/errors.go`, `middleware/errors.go`):
- тело любой ошибки HTTP - `huma.ErrorModel`: `title`, `status`, `detail`, при 422 - `errors[]` (`message`, `location`);
- у 5xx `detail` без подробностей, а сама ошибка уходит в лог запроса с request ID;
- из `errors[]` убраны значения из запроса (`value`): там может оказаться секрет;
- 404 и 405 от самого роутера и 500 после паники пишутся в той же модели;
- заголовок `X-Request-ID` есть в каждом ответе, в теле ошибки его нет. Если понадобится машинный код ошибки, добавим одно поле в обёртке над `huma.ErrorModel`, а не отдельный пакет.

# Эпик A. Каналы и лобби

## EFR-1. Домен каналов

**Тип:** Story

> **Как** игрок, **я хочу** открыть канал и получить код, **чтобы** позвать друга.

Пакет `internal/channel` без сети: типы, правила, реестр.

**Бизнес-правила**
- **BR-1.1.** Код канала - 6 цифр, первая не `0`. Генерируется `crypto/rand`, уникален среди открытых каналов. При коллизии - новая попытка, не больше 10, потом ошибка.
- **BR-1.2.** Токен игрока - 32 байта из `crypto/rand` в base64url без паддинга. Сравнение токенов - `subtle.ConstantTimeCompare`.
- **BR-1.3.** Открывший канал занимает `west` с позывным `Первый`. В одиночной смене `east` сразу занимает бот: позывной `Второй`, `ready: true`, `bot: true`.
- **BR-1.4.** Гость занимает `east` и получает первый свободный позывной из списка: `Первый, Второй, Заря, Гранит, Сокол, Факел, Гроза, Тайга`.
- **BR-1.5.** Войти в одиночный канал нельзя: снаружи он выглядит как несуществующий (`ErrNotFound`).
- **BR-1.6.** Войти в канал, где оба поста заняты, нельзя (`ErrFull`).
- **BR-1.7.** Реестр не держит больше `GAME_MAX_CHANNELS` каналов (`ErrTooManyChannels`).
- **BR-1.8.** Реестр безопасен для одновременного вызова из многих горутин.

**Подзадачи**
- [ ] EFR-1.a. Типы `Channel`, `Player`, `Post`, `Callsign`, доменные ошибки.
- [ ] EFR-1.b. Генерация кода и токена (генератор подменяется в тестах).
- [ ] EFR-1.c. Реестр: создать, найти по коду, найти по id, удалить.

**Критерии приёмки**
- [ ] Тест BR-1.1: генератор возвращает занятый код 9 раз -> успех, 10 раз -> ошибка.
- [ ] Тест BR-1.4: если у хозяина `Второй`, гость получает `Первый`.
- [ ] Тест BR-1.8: 100 горутин создают каналы одновременно, коды уникальны, `-race` молчит.

## EFR-2. HTTP: открыть канал и войти по коду

**Тип:** Story

**API** (подробно - раздел 2 контракта)

`POST /api/channels`
```json
// запрос
{"mode": "coop"}
// ответ 201
{"channelId": "c_7f3a…", "code": "482117", "token": "…"}
```

`POST /api/channels/{code}/players` - тело `{}`, ответ `200` того же вида.

**Бизнес-правила**
- **BR-2.1.** `mode` - только `solo` или `coop` (enum в DTO) -> иначе 422.
- **BR-2.2.** `code` в пути - `^[0-9]{6}$` (pattern в DTO) -> иначе 422. Код с ведущим нулём проходит формат, но таких каналов не бывает (BR-1.1) -> 404.
- **BR-2.3.** `ErrNotFound` -> 404, `ErrFull` -> 409, `ErrTooManyChannels` -> 503.
- **BR-2.4.** `channelId` не совпадает с кодом и не угадывается: это отдельный случайный идентификатор.

**Критерии приёмки**
- [ ] Table-driven тест обработчиков на все статусы из BR-2.1–2.3.
- [ ] Ручная проверка: фронтенд с `VITE_BACKEND=http` открывает канал и видит код. Сокета ещё нет, поэтому дальше «Связь с каналом…» - это ожидаемо.

## EFR-3. WebSocket: подключение и обмен сообщениями

**Тип:** Story · **Размер:** крупный, разбит на подзадачи

`GET /api/channels/{channelId}/ws?token=…`

**Бизнес-правила**
- **BR-3.1.** Апгрейд только с верным токеном этого канала -> иначе 401. Origin не из `GAME_WS_ALLOWED_ORIGINS` -> 403.
- **BR-3.2.** У каждого игрока одно активное соединение. Новое подключение с тем же токеном закрывает старое кодом 1000 и занимает его место.
- **BR-3.3.** Входящие сообщения больше `GAME_WS_MAX_MESSAGE` -> закрыть с 1009 (лимит чтения у библиотеки).
- **BR-3.4.** Сервер раз в 20 с шлёт ping. Нет pong за 10 с - соединение считается оборванным.
- **BR-3.5.** Запись в сокет не блокирует горутину канала (ADR-003): у каждого игрока буферизированный `outbox` и своя горутина записи.
- **BR-3.6.** Таймауты `http.Server` (`ReadTimeout`, `WriteTimeout`) не обрывают долгоживущий сокет. Как этого добиться (снять дедлайны после апгрейда, `http.ResponseController`) - разобраться и описать в комментарии.
- **BR-3.7.** Токен из query не попадает в access log (NFR-3).

**Подзадачи**
- [ ] EFR-3.a. Горутина канала (`inbox`, `select`, контекст) и подписка игроков.
- [ ] EFR-3.b. Апгрейд в `httpapi`, проверки BR-3.1, маскировка токена в логе.
- [ ] EFR-3.c. Пакет `ws`: горутины чтения и записи, ping/pong, кодирование JSON.
- [ ] EFR-3.d. Сразу после подключения игрок получает `{"type":"lobby", …}` (пока без правил EFR-4).

**Критерии приёмки**
- [ ] Тест на `httptest.Server`: подключиться, получить снимок лобби.
- [ ] Тест BR-3.2: второе подключение с тем же токеном - первое закрыто.
- [ ] Тест BR-3.5: «медленный» клиент, который не читает, не задерживает отправку второму игроку.
- [ ] `-race` молчит на всех тестах пакета.

## EFR-4. Правила лобби

**Тип:** Story

> **Как** игрок, **я хочу** выбрать позывной и нажать «Готов», **чтобы** смена началась, когда готовы оба.

Сообщения: `set_callsign`, `set_ready` от клиента; `lobby` и `error` от сервера (раздел 3.1 контракта).

**Бизнес-правила**
- **BR-4.1.** После **каждого** изменения оба игрока получают лобби целиком, каждый со своим `you`.
- **BR-4.2.** `set_callsign` неизвестного позывного - игнорируется. Позывной напарника -> `error callsign_taken`. Игрок уже готов -> `error callsign_locked`.
- **BR-4.3.** `set_ready: true`, когда в канале один игрок -> `error partner_missing`.
- **BR-4.4.** Оба готовы -> `phase: starting`, `countdown: 3`, дальше раз в секунду 2, 1. На нуле - `phase: shift`, `countdown: null`.
- **BR-4.5.** Кто-то снял готовность во время отсчёта -> `phase: lobby`, `countdown: null`, отсчёт остановлен.
- **BR-4.6.** Одиночная смена: «Готов» игрока сразу даёт `phase: shift`, без отсчёта.

**Критерии приёмки**
- [ ] Тесты на каждое правило. Время в тестах подменяется: отсчёт идёт от тиков, а не от `time.Sleep`.
- [ ] Ручная проверка: два браузера (второй в приватном окне) проходят лобби до предыстории; в одиночной смене - сразу предыстория.

## EFR-5. Обрывы связи и уборка каналов

**Тип:** Story

**Бизнес-правила**
- **BR-5.1.** Сокет оборвался (не код 1000) -> пост за игроком сохраняется, `connected: false`, напарник получает лобби.
- **BR-5.2.** Переподключение с тем же токеном в течение `GAME_RECONNECT_GRACE` -> `connected: true`. Игрок сразу получает лобби, а в смене - и снимок.
- **BR-5.3.** Не вернулся за `GAME_RECONNECT_GRACE`: в лобби пост освобождается; в смене - см. открытый вопрос в контракте. Пока: смена ставится на паузу, напарнику идёт строка рации «Напарник пропал из эфира».
- **BR-5.4.** Сокет закрыт кодом 1000 -> пост сразу свободен. Ушёл хозяин канала -> канал закрывается, сокет гостя закрывается кодом 1000.
- **BR-5.5.** Канал, в котором в лобби никого нет дольше `GAME_LOBBY_IDLE_TTL`, удаляется из реестра. Его горутина завершается.
- **BR-5.6.** По SIGTERM все горутины каналов завершаются, сокеты закрываются кодом 1001 (NFR-5).

**Критерии приёмки**
- [ ] Тесты BR-5.1–7.5 с подменённым временем.
- [ ] Тест на утечку горутин: после закрытия всех каналов число горутин возвращается к исходному (например, `go.uber.org/goleak` в тестах или `runtime.NumGoroutine`).

# Эпик B. Смена

Всё в этом эпике - порт `efir_frontend/src/lib/game/sim`. Пакет `internal/game` чистый (ADR-002, ADR-004). Тексты дословно из эталона.

## EFR-6. Правила, типы и помощники

## EFR-10. Волны и мутанты

**Тип:** Story · **Размер:** крупный, разбит на подзадачи

**Бизнес-правила: план ночи** (`planNight`)

- **BR-10.7.** Разовые сообщения (первые отметки у ворот, ревун вышел, туша ломится в баррикаду, мутанты у ядра) - один раз за ночь, ключи как в эталоне.

Ретранслятор разрушен - выбирает следующий. Ретрансляторов нет - идёт к ядру и висит в 3,8 от него. - **BR-22.3.** `fuel` - только днём, только в свой дизель, если он цел, в баке меньше `TANK_MAX` (3) и склад не пуст. Отказы - `flash` с текстами эталона (`fuelDiesel`). Заливку видят оба в журнале.
- **BR-22.4.** `demolish` по своему дизелю днём сливает одну канистру обратно на склад. Ночью -> `flash` «Ночью топливо из бака не слить.».
- **BR-22.5.** Ночью бак горит: канистра за `CANISTER_SEC` (40 с) даёт `CANISTER_GAIN` (20) ⚡. Дробь копится, в энергию уходят только целые. Бак опустел -> «Дизель заглох: бак пуст.». Сгоревшие канистры считаются по переходу через целое (`stats.burned`).
- **BR-22.6.** Работающий дизель шумит: мутант (кроме ревуна) ближе `DIESEL_PULL` (3) сворачивает к нему по своему полю путей и грызёт. Дизель заглох или сломан -> снова к ядру. Реплика «Мутанты идут на шум дизеля!» - раз за ночь на пост, напарнику своя.
- **BR-22.7.** Дизель сломали -> всё топливо в баке, и початая канистра, пропадает (`ceil`), запись в журнал, в сводке «вытекло».
- **BR-22.8.** На рассвете бригада чинит дизели: целому - полная прочность, сломанный ставится заново. Исключение - `noRepair` из просьб бункера (EFR-23).

**Критерии приёмки**
- [ ] Перенесены тесты эталона из блока «дизель и единый запас канистр»: старт, лимит бака и слив, горение, притяжение шумом, поломка и ремонт, строка «Топливо» в сводке.
- [ ] Тест BR-22.5: за 40 с ночи одна канистра даёт ровно 20 ⚡.

## EFR-23. Просьбы бункера

**Тип:** Story

> **Как** пост, **я хочу** вместе с напарником решать, на что бункер потратит наши ресурсы, **чтобы** выбор был общим и с последствиями.

Команда `vote {yes}`. Поля снимка: `card`, `shaft`, `openGate`. Эталон: `sim/cards.ts` (карточки, тексты, числа) и раздел «Просьбы бункера» в `simulation.ts`.

**Бизнес-правила: голосование**
- **BR-23.1.** Колода из 10 просьб тасуется один раз на смену. Утром дней 2–6 вытягивается первая, у которой выполнено `prepare`. Не подошедшие остаются в колоде. Сообщение в журнал и рацию.
- **BR-23.2.** Голосуют оба поста, бот тоже (BR-16.7). Голос один, переголосовать нельзя: `flash` «Голос уже отдан.». «За» нельзя, если пост не может заплатить: `flash` «Голосовать «за» нельзя: …».
- **BR-23.3.** Решается, как только проголосовали оба. Принято, только если оба «за» и оба могут заплатить в момент решения. Иначе отклонено, причина - в `note`.
- **BR-23.4.** Кто не проголосовал до начала ночи, тот «против». В `startNight` решение идёт после докладов дронов и дневной стройки бота, но до смены фазы и плана волны. Принятая «Тишина» включается здесь же.
- **BR-23.5.** Цена (`energy` ⚡ с каждого поста, `fuel` канистр со склада) списывается только при «принято».
- **BR-23.6.** Текст карточки - лор и намёк, без прямого «вы получите». Что вышло, игрок узнаёт по журналу. Тексты дословно из эталона.

**Бизнес-правила: карточки**

| id | Цена | Принято | Отказ |
|---|---|---|---|
| `lab` | 15 ⚡ | `fonShield += 1`: в следующий раз, когда в эфире не останется ревунов, Фон спадает сразу | - |
| `repair` | 20 ⚡ | ядро +25%, не выше 100. Выпадает, только если ядро ≤ 85% | - |
| `boiler` | 20 ⚡ | +1 канистра на склад | - |
| `vent` | - | +15 ⚡ каждому, `noRepair = max(noRepair, 2)` | - |
| `medblock` | 1 канистра | - | `noRepair = max(noRepair, 1)`. Выпадает, только если склад не пуст |
| `refugees` | - | +2 канистры. Баррикада с ворот снимается, до рассвета на них не поставить (`openGate`) | - |
| `silence` | - | эту ночь `jam` без `noise`. На старте ночи замеры выбирают ворота основного удара на 2 следующие ночи (`nextMains`, без повтора подряд), на рассвете их называют. Не в 7-й день | - |
| `reserve` | 3 канистры | канистры в НЗ (`locked`). Утром 7-го дня возвращаются +2 | - |
| `drone` | - | +10 ⚡ каждому, дрон сегодня не летает ни у кого | - |
| `shaft` | - | клетка шахты в 4–7 от ядра. Мутант (не ревун) в соседней клетке -> ядро −10%, опыт сорван. Ночь без этого -> +20 ⚡ каждому на рассвете | −10 ⚡ каждому, не ниже 0 |

- **BR-23.7.** `noRepair`: на каждом рассвете, пока больше нуля, уменьшается на 1, и дизели не чинятся. Если был сломанный или побитый - запись в журнал и в строку «Бункер».
- **BR-23.8.** Шахту видно в снимке ещё во время голосования (`shaft.pending: true`), строить на ней нельзя с того же момента.
- **BR-23.9.** Отладка во фронтенде: `?card=<id>` в dev-сборке с заглушкой даёт эту просьбу в первый день. Серверу это не нужно.

**Критерии приёмки**
- [ ] Перенесены тесты `cards.test.ts`: принято / разделились / таймаут / нет денег и по тесту на каждую карточку.
- [ ] Тест BR-23.4: голос только хоста и ночь -> отклонено, последствия отказа применены.
- [ ] Ручная проверка: смена вдвоём, оба видят голоса друг друга сразу.

# Эпик C. Голос

## EFR-18. Голос через WebRTC

**Тип:** Story · **Нужна работа фронтенда**

Сейчас голос - только эхо в браузере. Для двух людей звук идёт напрямую между браузерами (WebRTC), а сервер только помогает им соединиться.

**Бизнес-правила**
- **BR-18.1.** Сервер пересылает напарнику сообщения `rtc_offer`, `rtc_answer`, `rtc_ice` как есть, ничего в них не разбирая. Размер ограничен `GAME_WS_MAX_MESSAGE` (для SDP может понадобиться отдельный лимит побольше).
- **BR-18.2.** `GET /api/rtc/config` отдаёт список ICE-серверов (STUN, позже TURN с временными учётными данными).

**Приёмка:** два браузера в смене слышат друг друга через фильтр рации.
